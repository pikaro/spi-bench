# PubSub full-bus media workload limit

On 2026-05-03, after RS485 wiring was fixed, a 180s full-bus capture with master + media + io + gpu0 + gpu1 showed the final prototype bus shape was transport-stable: high-speed shared SPI to gpu0/gpu1 had no sustained tx failures or rx drops, RS485 stayed at ~100/s ingress, and the low-speed SPI link remained active. The limiting route was media-originated Beat traffic: media only published about 57-65/s while the audio/FFT/display workload was active, so media->gpu/media->io latency and target misses reflect source scheduling/workload limits rather than shared SPI routing capacity. The same run showed occasional `Audio::FftDisplay` mutex timeouts and a few transient low-speed SPI egress backpressure drops. Do not optimize PubSub/SPI around this without first optimizing or isolating the media FFT/display workload.
