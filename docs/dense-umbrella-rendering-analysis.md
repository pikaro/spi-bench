# DenseUmbrella Rendering Pipeline Analysis

Status: **evidence pass complete; converted into `docs/dense-umbrella-rendering-plan.md`**  
Date: 2026-08-26  
Scope: architectural evaluation of the LED rendering pipeline for a
mixed-capable WS2812B/SK9822 output expansion. This document preserves the
research record; implementation state and remaining acceptance work are tracked
in `docs/dense-umbrella-rendering-plan.md`.

> **Geometry revision (2026-08-27):** The physical design changed after this
> evidence pass from 72 to 60 LEDs per spoke. The 32×72 counts, projections,
> and 2×144 bench references below preserve the original decision record. The
> implemented 32×60 geometry, 960-pixel halves, and 2×120 bench contract are
> tracked in the rendering plan and current subsystem documentation.

## Requested target

- Add a `DenseUmbrella` geometry for 32 spokes with 72 LEDs per spoke.
- Preserve the existing snake routing semantics.
- Drive the new installation as two physical halves.
- Add SK9822 clocked output while retaining a sensible abstraction for WS2812B and, if practical, mixed hardware.
- Replace WS2812B temporal dithering-based low-brightness behavior with SK9822's 5-bit per-pixel hardware brightness, driven by the existing logical brightness range of 0..255.
- Keep the current frame rate and animation behavior unless analysis proves a geometry dependency or resource problem.
- Preserve the existing color, layer, blending, animation, and buffering behavior where their abstractions already fit.
- Treat brightness primarily as a predictable audience-intensity/safety control. The hardware change was motivated by approximately 800 full-brightness WS2812B LEDs being uncomfortably bright for festival attendees in a dark environment, not primarily by a desire for higher-fidelity low-light color rendering.

## Investigation rules

- Every conclusion will cite concrete code/document/library evidence.
- Hardware- or library-dependent claims will carry a confidence label.
- A blocking ambiguity affecting feasibility, correctness, or architectural scope will be raised before any implementation plan is treated as safe.
- Existing visual behavior is preservation-critical; cleanup opportunities are recorded separately from required migration work.

## Evidence and confidence labels

- **Verified**: directly established by repository code, build configuration, or the exact vendored/resolved library source.
- **High confidence**: supported by authoritative documentation or an unambiguous local dependency API, but not exercised on the target hardware.
- **Medium confidence**: reasoned from code and protocol behavior but dependent on an unresolved hardware/configuration detail.
- **Open**: requires owner input, exact hardware information, measurement, or a bring-up experiment.

## Baseline facts established

1. **Verified — distributed rendering:** GPU nodes render their own LED segments locally because full frames are intentionally not transported at the target 125 fps (`docs/overview.md`).
2. **Verified — synchronized presentation:** the current/legacy documentation says the master emits a 125 Hz present strobe on GPIO6 and both GPU nodes receive it on GPIO10 (`docs/overview.md`). The v2 generated netlist instead routes GPU0 strobe to GPIO10 and GPU1 strobe to GPIO4.
3. **Verified — current ownership shape:** GPU firmware has explicit compile-time group ownership; the documented current mapping interleaves four logical groups across two nodes (`gpu0`: groups 0 and 2, `gpu1`: groups 1 and 3) (`docs/overview.md`).
4. **Verified — relevant subsystem boundary:** topology, ownership, FastLED output, animations, drawing primitives, layering, and PubSub commands live under `include/LedTopology/` and `include/LedDisplay/`; `docs/animation-pipeline.md` is the subsystem guide (`docs/overview.md`).
5. **Verified — present public brightness semantics:** `/disp brightness` currently describes its 0..255 argument as the FastLED global-brightness value (`docs/commands.md`). Whether that API should remain output-type-neutral is under investigation.

## Pipeline map

```text
master commands / FFT / wheel / present strobe
                    |
                    v
AnimationEngine (GPU-local, HSV, logical coordinates)
  -> per-animation owned scratch
  -> seven persistent/cleared layer frames
  -> compositor
  -> triple-buffered owned HSV frame
                    |
                    v
LED output boundary
  -> HSV-to-RGB and output-floor policy
  -> protocol-specific brightness/dither policy
  -> physical-chain encoder/transport
                    |
                    v
one 1,152-pixel physical chain per GPU
```

The first three stages are substantially LED-protocol-neutral. The existing
`FastLedOutput` is the only hardware-output boundary, but it currently combines
several separable policies and a WS2812B-specific controller registration.

## Geometry and ownership findings

1. **Verified — current dimensions are compile-time configuration:** `LedTopologyStaticConfig` defines 4 strips × 4 segments per strip × 46 LEDs per segment = 736 physical pixels, 16 spokes, and 46 rings (`include/StaticConfig/LedDisplay.hpp`). The count arithmetic is already centralized and propagates into fixed buffer extents.
2. **Verified — the current logical map contains more than serpentine reversal:** `Umbrella::physicalFor()` first divides spokes into four-spoke strips, mirrors logical segment order within each strip (`0→3`, `1→2`, `2→1`, `3→0`), and only then reverses radial direction on odd physical segments (`include/LedTopology/detail/Umbrella.hpp`). A new surface that merely “snakes” does not automatically share this segment mirror.
3. **Verified — topology selection is not currently an abstraction:** `LedTopology/Facade.hpp` exposes one hard alias, `Umbrella = detail::Umbrella`, and engine/canvas code refers to `LedTopology::Umbrella` directly. Counts are configurable, but geometry policy is not selected through a type/config seam.
4. **Verified — ownership is contiguous physical grouping, independent of logical geometry:** `OwnedPixels` partitions the total physical index range into equal `groupPixelCount` blocks, maps configured physical group IDs into a node-local contiguous buffer, and subdivides each owned group evenly among configured data lines (`include/LedTopology/detail/OwnedPixels.hpp`). This is a good separation if each DenseUmbrella physical half is one contiguous physical chain.
5. **Verified — index widths remain sufficient:** the proposed 32 × 72 surface has 2,304 pixels, well within the current `uint16_t` logical, physical, and local pixel index types (`include/LedTopology/Interfaces/Types.hpp`). Per-spoke/radial coordinates also fit the current `uint8_t` fields.
6. **Verified owner contract — clarified target order and simple map:** owner input establishes monotonic spoke order, GPU0 as logical spokes 0..15, GPU1 as spokes 16..31, both chains starting at the inner ring, and alternating radial traversal. The complete global map is `physical = spoke*72 + (spoke is odd ? 71-radial : radial)`. Because spoke 16 is even, each GPU's local chain index zero is its half's inner LED. No old four-spoke mirror is present.
7. **Verified — existing ownership arithmetic fits the halves:** configure two equal groups, one owned group per GPU, and one physical output chain per GPU. Group 0 is physical 0..1151 and group 1 is 1152..2303. `OwnedPixels` then maps each selected group to local 0..1151 without a new lookup scheme.

## Animation and compositing findings

1. **Verified — LED-type-neutral core representation:** animation configs and renderers produce `HsvColor`; `LayerStack`, `Compositor`, and `PresentBuffers` store and manipulate HSV frames without referencing a physical LED protocol (`include/LedDisplay/detail/{AnimationEngine,LayerStack,Compositor,PresentBuffers}.hpp`). HSV→RGB conversion happens only in `FastLedOutput::show()`.
2. **Verified — geometry-scaled iteration:** canvas bounds, logical indexing, polar angle, strip radius, physical radius, and the common full-field iterator all derive from `Config::spokeCount` and `Config::ringCount` (`include/LedDisplay/Primitives/{Canvas,FieldCoordinates}.hpp`). The proposed 32×72 dimensions do not overflow their current intermediate arithmetic.
3. **Verified — current animations are local-frame compatible:** the engine supports an opt-in full-logical-frame path, but the current documented animations do not require it. Normal animations render only locally owned pixels through a precomputed logical-to-local map. Changing from two interleaved owned groups to one contiguous half per GPU does not change animation APIs.
4. **Verified — density-sensitive visual units exist by design:** several animation widths, trails, travel distances, and spacings are expressed in spokes or rings. Defaults therefore occupy a smaller fraction of a 32×72 surface than of a 16×46 surface. This is a visual-tuning change, not a mapping failure, and should not be altered during first bring-up.
5. **Verified — some behavior was explicitly tuned for 16 spokes:** examples include Lighthouse's minimum beam-width treatment and documentation, plus defaults/caps chosen to avoid 16-spoke aliasing in point/petal/symmetry effects. These need offline/hardware regression observation on 32 spokes, but do not prevent initial rendering.
6. **Verified — “local-frame compatible” does not mean local-only computation:** most field animations iterate all `Config::spokeCount × Config::ringCount` logical points on every GPU; `Canvas::pixel()` discards points whose logical-to-local entry is invalid. The new geometry therefore raises the common per-GPU field loop from 736 to 2,304 points (3.13×), even though each GPU owns only 1,152. This preserves distributed visual identity and rotation semantics but leaves approximately half of common field calculations unused on each node.
7. **Verified — sparse and dense animations scale differently:** `OrbitSparks`, `SpokeSweep`, `WheelIndicator`, and `DiagnosticFill` have bounded/sparse drawing cost; most other animations are O(total logical pixels). `Cymatic` adds a bounded source loop per point, `OrbitRing` adds a bounded comet loop per point, and `StainedCells` compares each point against up to seven seeds (six by default), making it a likely target worst case.
8. **Verified — each active animation also incurs owned-frame passes:** the engine clears the 1,152-pixel scratch before every active animation and blends that entire scratch into its layer afterward. At frame start each enabled layer is cleared or decayed, and composition blends every enabled nonzero-opacity layer over the output. Sparse animations therefore retain predictable full-owned-frame overhead even when they touch few LEDs.
9. **Verified — the normal show can contain multiple animations:** the engine permits 32 active slots. Master orchestration normally keeps one persistent FFT animation, but a visual transition deliberately enables and renders both FFT layers for a 10-second crossfade. Transient/effect/wheel/debug layers may coexist. Timing acceptance must cover the real concurrent mix, particularly `StainedCells`↔another dense FFT animation, rather than a single-animation microbenchmark.

## Output backend and FastLED findings

1. **Verified — protocol coupling is narrow but policy coupling is not:** the concrete `WS2812B` template appears only in `FastLedOutput::_addLine()`. However, the same class also owns controller count/pins, HSV→RGB conversion, output value/luma floors, global brightness, dithering state, and cadence recovery. A safe expansion should preserve the narrow frame API while making output hardware policy explicit inside/below this boundary.
2. **Verified — exact dependency:** both GPU environments resolve FastLED 3.10.3 (`platformio.ini`, `.pio/libdeps/gpu1/FastLED/library.json`). That release provides `SK9822` and `SK9822HD` clocked controllers with a default 12 MHz clock (`FastLED/src/chipsets.h`).
3. **Verified — FastLED clocked hardware output is opt-in on ESP32:** `FastLED/src/fastspi.h` selects `ESP32SPIOutput` only when `FASTLED_ALL_PINS_HARDWARE_SPI` is defined. The project does not define it, so a naive `WS2812B`→`SK9822` controller substitution selects the software-SPI template.
4. **Verified — the available FastLED ESP32-S3 hardware path conflicts with this firmware shape:** FastLED 3.10.3 forces its Arduino `SPIClass` backend to `FSPI` for ESP32-S3 (`FastLED/src/platforms/esp/32/fastspi_esp32.h`). ESP-IDF defines `FSPI_HOST` as `SPI2_HOST`; the GPU PubSub slave already initializes `BusId::Bus2` as `SPI2_HOST` (`src/gpu/config.hpp`, `include/Wire/Spi/detail/platform/PlatformESP32.hpp`). Two independent drivers cannot own that peripheral concurrently.
5. **Verified — framework mismatch:** this project is `framework = espidf`, and the installed ESP-IDF framework does not provide Arduino ESP32 `SPI.h`. Enabling FastLED's built-in ESP32 hardware-SPI path as-is would therefore introduce an unavailable Arduino API even before the host conflict is addressed.
6. **Resolved — intended LED SPI host:** the generated hardware netlist establishes freely routable LED CLK/DATA pins distinct from each node's PubSub SPI2 pins. The robust transport direction is therefore an ESP-IDF SPI3 master backend, without adding Arduino or moving PubSub.
7. **Verified — target pins from generated hardware netlist:** `schematic/build/perfboard-v2.config-netlist.json` routes GPU0 SK9822 CLK/DATA to GPIO7/GPIO8 and GPU1 CLK/DATA to GPIO10/GPIO13 through a 74AHCT125 level shifter. These pins do not overlap either GPU's new PubSub signal pins in that netlist.
8. **Verified — SPI3 is the appropriate available hardware host:** ESP32-S3 exposes independent SPI2 and SPI3 general-purpose controllers, both DMA-capable. The current ESP-IDF 5.5.3 sources used by the project include SPI3 master support and benchmark ESP32-S3 SPI at 40 MHz. Espressif documents GPIO-matrix-routed SPI as equivalent to IO_MUX routing at 40 MHz or below; the target LED pins can therefore be routed to SPI3. Sources: local ESP-IDF `spi_master`/SoC sources and [Espressif SPI master documentation](https://docs.espressif.com/projects/esp-idf/en/v4.4.4/esp32s3/api-reference/peripherals/spi_master.html).
9. **Verified estimate — 40 MHz is not required for frame rate:** for 1,152 pixels, FastLED 3.10.3's SK9822 framing emits 4 start bytes + 4 bytes/pixel + 148 end bytes = 4,760 bytes. Wire times are approximately 4.76 ms at 8 MHz, 3.81 ms at 10 MHz, 3.17 ms at 12 MHz, 1.90 ms at 20 MHz, and 0.95 ms at 40 MHz. These are protocol-time estimates from the exact library framing, not hardware measurements.
10. **High confidence — recommended initial transport direction:** keep PubSub on ESP-IDF SPI2 slave and give LED output an ESP-IDF SPI3 master device with no CS line, mode 0, MSB-first, DMA-capable preallocated storage, and a conservative 10–12 MHz initial clock. Raise the clock only after logic-analyzer and full-chain testing. The MCU supports 40 MHz, but the installed SK9822 variant, 74AHCT125 edge quality, connectors, wire length, and 1,152-device regenerated clock/data chain determine the reliable system limit.
11. **Verified — I2S is technically possible but not supported by the resolved FastLED path:** ESP32-S3 has two DMA-backed I2S peripherals and can emit a BCLK plus serial data, so a custom SK9822 serializer could be built. FastLED 3.10.3's included ESP32-S3 I2S implementation is specifically a clockless-LED parallel driver and contains no SK9822/APA102 path. Using I2S here would therefore be a larger custom backend with word-select/framing accommodations and no advantage over the free SPI3 peripheral.
12. **Verified — current FastLED releases do not remove this local constraint:** the project resolves 3.10.3; 3.10.4 is the latest tagged release found during research, while the newer ESP-IDF-native/channel SPI manager documented on FastLED `master` is unreleased relative to those tags. A critical output design should not depend on unreleased `master` behavior without an explicit dependency decision and hardware proof.
13. **Verified — current output configuration models pins at the wrong semantic level:** `dataLineCount` plus `outputPins[]` describes two independent WS2812B data chains. The new board has one physical chain per GPU with a data/clock pair. Treating both pins as generic “lines” would make ownership subdivision incorrect. Topology ownership should describe the single contiguous chain; a clocked output descriptor/policy should own its data pin, clock pin, SPI host, clock rate, wire color order, and protocol framing.
14. **Verified — the frame API itself is already sufficient:** `Display` needs only output `begin`, `setBrightness(uint8_t)`, `show(span<const HsvColor>)`, and `deinit`. No animation, compositor, command, or present-buffer caller needs to know whether the backend is WS2812B or SK9822. A compile-time concrete backend/policy fits the existing static configuration and avoids virtual/runtime dispatch in the hot path.
15. **Verified — FastLED global policy limits true mixed output:** the current class calls global `FastLED.setBrightness()`, `setDither()`, and `show()`. If WS2812B and SK9822 controllers ever coexist on one MCU, their dither/brightness transport policies cannot be independently represented through these global calls. The new architecture should keep the frame API open to such a backend, but production-v2 does not need a speculative mixed-controller implementation: each GPU has one SK9822 chain.
16. **High confidence — an asynchronous SPI3 transaction is compatible with the existing buffers:** the HSV present frame is immutable during `show()`, and an output-owned encoded/DMA buffer can remain untouched while the engine renders the next HSV frame. A one-transaction-in-flight contract could overlap the 3.17 ms 12 MHz wire interval with rendering, provided the next presentation explicitly reaps/completes the prior bounded transaction before reusing the wire buffer. This is a timing provision to evaluate, not an implementation decision yet.
17. **Recommended concrete boundary:** retain FastLED's already-used HSV→RGB renderer, but do not use its Arduino `SPIClass` clocked transport for v2. A compile-time-selected `Sk9822SpiOutput` can encode start/pixel/end frames into preallocated DMA-capable memory and submit them through ESP-IDF SPI3. The existing WS2812B/FastLED controller can remain its own concrete backend if legacy hardware remains a supported target. A future composite backend could provide mixed outputs without contaminating the animation API; it is not required for the one-SK9822-chain-per-GPU v2 build.
18. **Verified — asynchronous driver primitives exist in the exact framework:** ESP-IDF 5.5.3 provides `spi_device_queue_trans()` plus `spi_device_get_trans_result()`, permits `spics_io_num = -1`, and supports pre-sized DMA transfers. The driver can allocate a temporary DMA buffer for unsuitable storage, but that would add hidden allocation/copy behavior; the critical backend should instead own a verified DMA-capable, correctly aligned, fixed buffer.

## Brightness and dithering findings

1. **Verified — existing command semantics can remain 0..255:** the PubSub command, engine atomic update, and `FastLedOutput::setBrightness(uint8_t)` already carry the complete logical range without embedding WS2812B-specific behavior.
2. **Verified — FastLED 3.10.3 already uses the hardware field for ordinary `SK9822`, but its exact mapping need not be copied:** on non-AVR platforms `FASTLED_HD_COLOR_MIXING` defaults to 1. `SK9822Controller` maps the FastLED global brightness from 0..255 to one SK9822 5-bit field value 0..31, writes that same level for every pixel, and keeps the RGB color values separate (`FastLED/src/{crgb.h,chipsets.h,pixel_controller.h,cled_controller.cpp}`). Its floor-division formula plus nonzero safeguard creates a lopsided first bucket described below. A project-owned encoder should specify its mapping contract explicitly rather than inherit incidental library behavior.
3. **High confidence — quantize exactly once:** if a FastLED controller performs encoding, manually reducing 0..255 to 0..31 before calling `FastLED.setBrightness()` would cause a second mapping and produce incorrect brightness. With the recommended project-owned ESP-IDF encoder, preserve the 8-bit logical API and perform one explicit project mapping directly into the emitted 5-bit header. Verify it with host byte tests and a logic analyzer.
4. **Verified — dithering can be disabled at the existing boundary:** `FastLED.setDither(DISABLE_DITHER)` applies to every registered controller. `_trackDitherCadence()` is already a no-op when `Config::temporalDithering` is false. Output-type policy must ensure SK9822 selects false rather than relying on the current default true.
5. **Resolved — retain FastLED-compatible nonzero semantics initially:** FastLED's mapping is not a uniform 256-bin round-to-nearest mapping: logical 0→0, logical 1..16→1 after its nonzero safeguard, and higher values are truncated into 1..31. The owner accepts this policy now that it is clear all 31 nonzero hardware codes remain reachable. It preserves the useful invariant that a nonzero brightness request cannot accidentally blank the installation.
6. **Clarified owner contract — value/luma floors are configurable WS2812B workarounds, not an SK9822 default-policy decision:** `_brightnessAdjustedFloor()` and `_clampLowLuma()` predict post-output light using the WS2812B/FastLED 8-bit brightness scale. The owner confirms these floors exist to manage WS2812B low-value behavior and expects the existing options to remain available, with zero disabling them. This analysis does not choose new defaults. If a floor is enabled while using SK9822, any documented post-brightness semantics must use the actually emitted 5-bit level; when disabled, no floor filtering should occur.
7. **Recommended semantic boundary:** retain 0..255 as the public/display brightness, quantize exactly once inside the clocked-output policy to one 0..31 hardware level used for every pixel header, leave each pixel's RGB bytes at the animation renderer's full output, and keep dithering/value-floor/luma-floor choices explicit in configuration rather than hard-coded into the LED-type backend. This prevents the animation and command layers from learning LED protocol details without removing useful experimental controls.
8. **Verified — `SK9822HD` does not merely enable hardware brightness:** ordinary `SK9822` and `SK9822HD` both write the hardware 5-bit header in this build. `SK9822HD` selects FastLED's `kFiveBitGammaCorrectionMode_BitShift`: for every pixel it applies a gamma expansion, applies color/global scaling in higher precision, chooses a pixel-dependent 1..31 hardware level from that pixel's intensity, and compensates its RGB bytes for the chosen level (`FastLED/src/fl/five_bit_hd_gamma.h`). This is an alternative color-transfer/precision algorithm, not the required global-brightness feature switch.
9. **Selected initial direction — ordinary global-brightness semantics:** use ordinary `SK9822` behavior for v2 bring-up because it exactly expresses the immediate operational requirement—one installation-wide brightness setting adapts the complete display between dusk/dawn, evening, and deep-night conditions while animation RGB relationships remain otherwise unchanged. `SK9822HD` is not part of the initial phase. Adopting it later would be an explicit alternative color-transfer experiment because it changes gamma, gradients, color balance, and uses pixel-dependent header levels.
10. **Verified — SK9822 provides all 32 hardware codes; FastLED alone creates the 1..16 collapse:** the wire header contains five brightness bits, so the hardware accepts codes 0..31 (off plus 31 nonzero levels). FastLED 3.10.3 first computes `floor(brightness*31/255)`: logical 1..8 would become zero, then its nonzero safeguard raises them to level 1; logical 9..16 already map to level 1. Thus 1..16→1 is a FastLED mapping artifact, not evidence of 4-bit or 16-level hardware. It does not discard half of the hardware levels: every nonzero level 1..31 remains reachable, but it wastes eight logical input codes by making the level-1 bucket twice as wide as the others.
11. **Available but not selected for initial bring-up — even ceiling mapping:** because v2 owns the encoder, a nonzero-preserving even mapping could use `level = value == 0 ? 0 : ceil(value*31/255)`, implemented with bounded integer arithmetic. This would map 1..8→1, 9..16→2, and 247..255→31. The owner has accepted FastLED's existing floor-plus-clamp behavior for the initial implementation, so the ceiling variant should remain only a documented future tuning option rather than silently changing the transfer curve during migration.
12. **Deferred `SK9822HD` value:** the HD algorithm is not required to obtain hardware brightness and is not selected for v2 bring-up. It still applies the installation-wide 0..255 global brightness before encoding each pixel, so it may eventually preserve the same ambient-condition control while also producing finer gamma-corrected color through joint RGB/5-bit representation. It is a deferred visual enhancement experiment, not only a fallback for insufficient range; its output must be compared deliberately because it changes the color-transfer function and emitted header levels.
13. **Safety-oriented control requirement:** regardless of ordinary versus HD encoding, the selected user brightness and any installation maximum must bound the emitted output predictably. Startup must prepare the intended brightness and a black frame before shared active-low `LED_EN` is asserted, so reset/reconnect cannot produce an uncontrolled full-bright flash. Exact safe operating limits are an owner/venue decision to establish experimentally; this analysis does not invent one.
14. **Provision without initial implementation — separate encoding from transport:** the SPI3 backend should not fuse ESP-IDF transaction ownership with ordinary-SK9822 color/header calculations. A small pure frame-encoder boundary is already required for host byte tests and DMA formatting; keeping it separate permits a later HD encoder experiment without changing topology, animation, buffering, synchronization, or SPI lifecycle. Initial scope still contains exactly one production encoder: ordinary SK9822.
15. **Verified rationale / assessed quality of FastLED's clamp:** FastLED issue #1908 reported that ordinary SK9822 output went completely dark for `setBrightness(1..8)` after the floor mapping was introduced. The reporter explicitly requested that every nonzero public brightness map to at least hardware level 1. FastLED's current `if (bri == 0 && brightness != 0) bri = 1` is the smallest compatibility fix for that request while retaining its pre-existing floor formula. It is therefore understandable as a local bug fix, but it is not a principled 256→32 quantizer: a ceiling mapping satisfies the same nonzero-preservation invariant while distributing the logical range evenly.
16. **Selected control model — intensity and off are separate user concepts:** the owner wants normal brightness to control ambient-appropriate intensity while a future rotary-encoder `ButtonMenu` action controls whether the display is on. The low-level encoder must still define logical 0 as hardware code 0 for tests, startup, failure handling, and backward compatibility, but the future UI off action should blank output without overwriting the remembered nonzero brightness. The shared `LED_EN` level-shifter gate is a startup/electrical-safety control, not a display-off mechanism: disabling clock/data cannot extinguish SK9822 pixels that have already latched a frame.

## Timing, CPU, and memory findings

1. **Verified estimate — SK9822 wire time:** see output finding 9. At the resolved library's conservative 12 MHz default, a complete half-frame consumes about 3.17 ms of the 8 ms period if transmission is blocking. SPI DMA can avoid consuming CPU during that interval, but whether the render task blocks waiting for completion depends on the future backend API.
2. **Open — end-to-end 125 fps feasibility is not established by wire time alone:** current measured render maxima were 3.31–3.73 ms for 368 locally owned pixels, while the new per-GPU count is 1,152 (3.13×). Rendering is animation-dependent and not safely assumed linear, but the count increase makes CPU/render time a more serious risk than SPI at 12 MHz. A naive 3.13× extrapolation would exceed the 8 ms period and is only a risk indicator, not a prediction.
3. **Verified estimate — straightforward static storage remains modest:** assuming the verified three-byte `HsvColor`/`CRGB` layouts, the seven layer frames plus scratch, triple present frames, RGB staging, two logical maps, and full-logical scratch grow from about 18,400 bytes to 57,600 bytes per GPU (56.25 KiB). One preformatted FastLED-compatible SK9822 DMA frame is another 4,760 bytes if stored in addition to RGB staging. This excludes small control structures and driver descriptors.
4. **Verified — GPU memory context:** each GPU target is an ESP32-S3FH4R2 configured with 2 MiB Quad-SPI PSRAM. The fixed `std::array` members are currently ordinary static/BSS storage; `CONFIG_SPIRAM_ALLOW_BSS_SEG_EXTERNAL_MEMORY` is disabled, so they should be budgeted as internal memory unless deliberately placed elsewhere. Per owner direction, RAM is a capacity check rather than a cleanup driver: preserve simple fixed, triple, layer, and scratch buffers if the final link and runtime low-water measurements remain safe.
5. **Recommended performance acceptance:** retain 125 fps initially, then measure render, encode, transfer-wait, total step, missed strobe, and repeated-present maxima for every animation plus the two-animation FFT crossfades. Do not lower frame rate or refactor animations merely from scaling estimates. If timing fails, the first low-risk levers are SPI/render overlap and owned-point iteration; visual parameter retuning is unrelated.
6. **Verified baseline build:** an unmodified `gpu0` diagnostic build completed successfully on 2026-08-26 and linked at 164,112 / 327,680 bytes of reported internal RAM (50.1%). `Display` is currently 30,528 bytes by debug type layout. Adding the conservative 39,200-byte geometry/buffer delta plus a separate 4,760-byte wire frame projects to about 208,072 bytes (63.5%), leaving about 119,608 bytes before runtime allocations. This projection is encouraging but is not a substitute for the final v2 linked image and on-device internal-heap low-water measurement.

## Risks and remaining decisions

1. **Resolved direction, still requires implementation proof — SPI peripheral ownership:** keep PubSub on SPI2 and use an ESP-IDF-native SPI3 master LED backend. The stock FastLED 3.10.3 hardware-SPI adapter remains unsuitable because it selects Arduino FSPI/SPI2.
2. **Resolved owner contract — topology endpoints:** GPU0 owns spokes 0..15 and GPU1 owns 16..31; both physical chains begin at their half's inner LED.
3. **Resolved v2 bring-up alignment — GPU pin map:** `src/gpu/config.hpp` now matches the generated v2 netlist, including GPU1 LED clock on GPIO10, LED data on GPIO13, and present strobe on GPIO4. The assembled board has so far passed no-short and MCU-enumeration checks; physical signal-order verification remains part of LED bring-up.
4. **Open hardware verification — exact LED variant and color order:** the strips were purchased from BTF-Lighting through Alibaba, a known LED-strip vendor, but the repository has no exact listing/vendor datasheet or chip marking. The exact silicon revision, guaranteed CLK limit, end-frame behavior, and RGB wire order therefore remain hardware-test items. This does not block conservative 10–12 MHz bring-up with byte-level waveform and primary-color verification.
5. **High — 125 fps render headroom:** dense animations currently compute the entire logical surface on both GPUs, and orchestrated FFT crossfades double the active dense field work. This must be treated as a measured bring-up gate; a successful SPI waveform alone is not pipeline acceptance.
6. **Accepted hardware constraint / required startup contract — shared output enable:** GPU1 GPIO9 drives pins 1, 4, 10, and 13 of the shared 74AHCT125, whose enables are active-low; R22 pulls the net up to GPU1 3.3 V, so both GPUs' clock/data outputs are safely disabled during reset. Pulling GPIO9 low enables all four buffers at once. The owner confirms this GPU1 ownership was semi-intentional because the master and ESP32-S3 Zero's fragile top pads have no pins remaining. Firmware must therefore define a robust condition for enabling both GPUs' outputs only after their clock/data pins are known-idle and the output path is ready.
7. **Configuration requirement — SK9822 output floors:** retain the existing zero-disables value/luma-floor options and let the selected display configuration turn them on or off. Do not infer or hard-code an SK9822 default from their WS2812B origin. If enabled, define and test their behavior against the quantized 5-bit hardware brightness actually transmitted.
8. **High — minimum useful brightness and startup flash:** ordinary SK9822's first nonzero level is 1/31, while the final installation triples the original approximate LED count. The 2×144 physical prototype running full production frames must establish whether this is sufficiently dim in a representative dark environment. Separately, the shared level shifter must remain disabled until brightness state and a black output frame are prepared.

## Cleanup opportunities (non-migration scope)

1. **Performance-only, measurement-gated:** precompute an owned logical-point iteration table when the rotation map changes, then let dense field animations evaluate only the 1,152 points that can land on the node. This could remove roughly half of dense field math without changing logical coordinates, but it touches shared animation primitives and must have render-trace/visual regression proof.
2. **RAM-only, currently not recommended:** no registered animation requires the full-frame path, so its 2,304-pixel scratch plus identity map would consume about 11.25 KiB per GPU without present use. Likewise disabled layers still reserve frames. The owner has explicitly prioritized uncomplicated fixed storage when capacity allows; leave these structures intact unless a linked-image/runtime measurement creates a real constraint.
3. **Naming/API cleanup required by migration:** rename hardware-neutral user/docs semantics from “FastLED brightness” to “display brightness,” and stop using WS2812B-shaped `dataLineCount`/`outputPins` as the clocked-chain hardware model. This is correctness-oriented cleanup at the output boundary, not graphics behavior cleanup.
4. **Preservation rule:** do not combine geometry bring-up with animation constant retuning, compositor changes, HSV conversion changes, layer-policy changes, or buffer-count reductions. Capture deterministic host traces for the old topology before structural changes and compare them after each protocol-neutral refactor.
5. **Verified test-tool opportunity:** the host renderer already exercises the real animation, layer, compositor, rotation, and topology code and writes deterministic logical-order traces. Its build wrapper currently hardcodes the old geometry and single-owner configuration. The expansion plan should add compile-time old/dense and full/GPU-half variants, then prove that recombining GPU0 and GPU1 DenseUmbrella traces is bit-identical to a full-owner logical trace.

## Action-plan candidates

This is the concrete sequence the next implementation plan should refine after
the blocking owner inputs are resolved:

1. **Freeze evidence and remaining decisions.** Treat GPU ownership as fixed at 0..15 and 16..31 and shared GPU1-controlled `LED_EN` as an accepted board constraint. Preserve explicit dithering/value-floor/luma-floor configuration, including zero-disables semantics, without choosing new defaults in the backend. Record the exact purchased strip/listing if available, determine wire color order by the initial primary-color test, and define shared-enable startup coordination. Save old-topology deterministic traces for every animation and representative multi-layer/crossfade fixtures.
2. **Introduce the compile-time topology selection.** Add `DenseUmbrella` with 32×72 counts and the monotonic serpentine map; select it through one topology facade/policy. Configure two ownership groups and one chain per GPU. Add exhaustive host assertions for every logical↔physical endpoint, boundary, parity, ownership, and rotation case.
3. **Separate output contract from implementation.** Keep `Display` calling the existing small lifecycle/frame API. Move WS2812B/FastLED registration and policy into a clockless concrete backend, and select a new SK9822/SPI3 concrete backend at compile time. Do not add runtime virtual dispatch or an unneeded mixed-controller implementation.
4. **Build a pure ordinary-SK9822 encoder before hardware I/O.** Preserve the selected FastLED HSV→RGB conversion, encode one globally quantized 5-bit brightness level into every pixel header, leave RGB output otherwise unscaled by global brightness, make RGB wire order explicit, and reproduce the accepted start/end framing. Keep dithering and value/luma floors as explicit configuration controls rather than protocol constants. Host-test exact bytes for 0/1/31/32/1152 pixels, all 0..255→0..31 brightness boundaries, black/off, primary colors, enabled/disabled floor behavior, and invalid frame sizes. Keep the encoder pure and independent of SPI3 transport so a later HD experiment is contained, but do not implement or tune HD in this phase.
5. **Add the ESP-IDF SPI3 transport.** Use the v2 pins (GPU0 CLK7/DATA8; GPU1 CLK13/DATA10), no CS, mode 0, MSB first, a bounded queue depth of one, and an output-owned DMA-capable frame. Start synchronously at 10–12 MHz for simplest waveform proof; preserve the API seam needed to queue one frame asynchronously if measured timing requires overlap.
6. **Align the rest of the v2 pin map before enabling outputs.** Move PubSub SPI/attention/CS and GPU1 strobe to the generated-netlist pins. Hold shared active-low `LED_EN` disabled until both output pin pairs are known-idle and a deliberate system readiness condition is met. Emit no uncontrolled clock edges during startup/deinit/failure.
7. **Electrical, brightness-safety, and waterproof bench bring-up with production code.** Build the exact final 32×72 geometry, two-half ownership, full 1,152-pixel-per-GPU buffers, full SK9822 encoder, and final SPI timing. Attach 144 physical LEDs to each GPU, laid out as that half's first two 72-pixel serpentine spokes. Each GPU must still transmit the complete 4,760-byte/1,152-pixel half-frame; the absent downstream LEDs simply do not display their frames. With outputs initially disabled, set brightness and prepare black before enable, then verify idle levels, absence of startup flashes, start/pixel/end bytes, 0..31 headers, black/off, RGB order, all brightness levels, both chain starts, spoke reversal, continuous repeated operation, power behavior, connectors, sealing, and waterproof construction. Assess the ordinary global levels—especially the lowest few—in representative dusk, evening, and deep-night conditions. This is not a reduced geometry, reduced render, or reduced transmission test.
8. **Full pipeline acceptance at 125 fps on the 2×144 physical bench.** Because the code still renders, encodes, and transmits the full final topology, record the real link RAM, internal/external heap low water, task stack, render, encode, queue, wait, show/wire, total step, missed strobe, repeated frame, and active animation counts here. Exercise every animation, maximum realistic concurrent effects, and all orchestrated 10-second FFT crossfades for a sustained run. A pass establishes computational and transport feasibility before committing to the complete 2×1,152 physical build; it cannot expose signal/power faults that arise only farther down the final chains.
9. **Optimize only the failed dimension.** If wire wait is the issue, queue one DMA transfer and overlap it with next-frame rendering. If dense field math is the issue, add regression-proven owned-point iteration and stitch both GPU traces to prove bit-identical output. Reduce frame rate only after those measurements; do not alter animation constants as a timing fix.
10. **Visual regression and optional tuning later.** Compare old and DenseUmbrella host/hardware captures, document density-dependent differences, and make any aesthetic retuning a separate reviewed change after geometry, signal, brightness, and timing correctness are stable.
